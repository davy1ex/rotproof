# Use cases: как применять комплект

Общий цикл: сначала анализ и план, затем явное решение владельца, потом ограниченная реализация. После завершённого среза агент отчитывается, задаёт один вопрос о понимании изменённой области и после ответа сверяет его с источниками. Только затем владелец принимает результат и отдельно решает вопрос о commit. Не начинай реализацию по одному лишь плану агента.

| Сценарий | Prompt | Результат первого этапа | После утверждения |
| --- | --- | --- | --- |
| Новый проект | `prompts/draft-product.md`, затем `prompts/initialize-project.md` | Черновик продукта, карта проекта и первый срез | Заполнить документы, реализовывать утверждённый срез |
| Существующий проект с кодом | `prompts/adopt-existing-project.md` | Карта существующих правил/документов и план внедрения | Объединить только одобренные документы и ссылки |
| Новая фича | `prompts/propose-feature.md` | Сценарий, границы, критерии и решение о необходимости PRD | `prompts/implement-approved-slice.md`, затем проверка понимания изменённого среза |
| Рефакторинг | `prompts/propose-refactor.md` | Цель изменения структуры и критерии сохранения поведения | `prompts/implement-approved-slice.md`, затем проверка понимания изменённого среза |
| Планирование фич/майлстоунов | `prompts/plan-roadmap.md` | Предложение roadmap без изменений файлов | Каждую фичу проектировать отдельно |
| Product / PRD | `prompts/draft-product.md`; для фичи — `prompts/propose-feature.md` | Черновик `PRODUCT.md` или решение о feature PRD | После одобрения обновить документ |
| Проверка понимания проекта | `prompts/check-project-understanding.md` | Один вопрос по фактам репозитория без ответа и подсказок | Ответ владельца и фактчек с источниками; по желанию следующий вопрос |

## 1. Инициировать новый проект

Скопируй `AGENTS.md` в корень проекта, а `docs/` — в его документацию. Сначала дай владельцу подготовить продуктовый замысел через `prompts/draft-product.md`; после его утверждения запусти `prompts/initialize-project.md`. Утверди первый вертикальный срез отдельно. Не заполняй архитектуру технологическими предположениями.

## 2. Внедрить комплект в существующий проект

Не копируй шаблоны поверх действующих файлов. Сначала используй prompt внедрения: агент инвентаризирует правила, документы, решения, код и незакоммиченные изменения, затем предложит карту переноса и канонические пути. После явного утверждения переноси только согласованное, сохраняя смысл существующих решений. Не создавай параллельные пути, различающиеся только регистром букв.

## 3. Разработать фичу

Передай идею в `prompts/propose-feature.md`. Получи план и критерии без изменений файлов. Утверди один срез и решения, которые от тебя требуются; затем заполни блок задания в `prompts/implement-approved-slice.md`. После реализации агент покажет результат и проверки, задаст один вопрос по изменённой области и после твоего ответа сверит объяснение с источниками. Затем ты решишь, принимать ли результат и коммитить его.

## 4. Провести рефакторинг

Да, это отдельный use case: успех означает улучшить согласованное внутреннее свойство при сохранении внешнего поведения. Используй `prompts/propose-refactor.md`, затем общий prompt реализации с последующей проверкой понимания. Если меняется поведение, согласуй это как отдельную фичу или явно расширь утверждённый сценарий.

## 5. Планировать фичи и майлстоуны без реализации

Используй `prompts/plan-roadmap.md`. Он не меняет файлы и возвращает результаты для пользователя, зависимости, критерии завершения и решения-гейты. Даты, приоритеты и обязательства указывай только если их задал владелец. Каждый майлстоун после утверждения разбивается на отдельные срезы.

## 6. Создавать Product и PRD

`docs/PRODUCT.md` — единый источник целей продукта, пользователей, потребностей, границ и ключевых сценариев. Подготовь его через `prompts/draft-product.md`.

PRD не нужен для каждой небольшой фичи. Для крупной или неоднозначной фичи используй `docs/FEATURE-PRD-TEMPLATE.md` после уточнения через `prompts/propose-feature.md`. PRD уточняет один продуктовый сценарий и не дублирует Product. Черновик становится `Accepted` только после явного решения владельца.

## 7. Проверить понимание проекта

После каждого завершённого среза проверка понимания запускается как часть `prompts/implement-approved-slice.md`. Отдельно используй `prompts/check-project-understanding.md`, когда хочешь проверить уже существующую область проекта вне реализации.

После ответа агент проверяет каждое фактическое утверждение по коду и документам, приводит пути и номера строк, отделяет явно задокументированный замысел от вывода и говорит «не удаётся проверить», если источников недостаточно. Это учебный разбор, не оценка человека и не gate качества кода: баллы и pass/fail не используются, файлы не меняются.
